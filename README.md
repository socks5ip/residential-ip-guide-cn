## 一、住宅IP是什么，为什么比机房IP贵

**住宅 IP（Residential IP）** 是由民用宽带运营商（ISP）分配给家庭用户的 IP 地址。它的技术特征不在速度或带宽，而在 **ASN（自治系统号）归属**：这个 IP 所在的网段由 AT&T、Comcast、Verizon、NTT、SoftBank、中国电信、中国联通这类**民用宽带运营商**持有，而不是由 Amazon、阿里云、DigitalOcean 这类云厂商或 IDC 持有。

风控系统判断一个访问者的可信度时，看的第一层信号就是这件事。机房 IP 的 ASN 属于 hosting 类别，意味着「这个地址背后是一台服务器」；住宅 IP 的 ASN 属于 ISP 类别，意味着「这个地址背后大概率是一个家庭」。前者天然被扣分，后者天然得分。

**为什么贵？** 不是商家炒作，是物理限制。机房 IP 可以批量生成、批量回收，一条物理服务器上能跑几百个 IP；真实民宅线路每条宽带能分配的 IPv4 数量极少，扩容必须真实装机、真实拉线。供给曲线完全不同，价差是结构性的。

一个粗略的量级感（2026 年 10 月国内可购平台的实际区间）：

| 类型 | 典型月价 | 说明 |
|---|---|---|
| 机房 IP | 2–5 元起 | 供给充足，价格由带宽决定 |
| 长效静态（机房/城域网固定 IP） | 2–6 元起 | IP 固定，但 ASN 不是 ISP |
| 静态住宅 IP（真家宽） | 4–13 元起 | 供给稀缺，价格由 IP 资源决定 |
| 海外独享静态住宅 | 更高，通常按 IP 单条计价 | 跨境线路成本叠加 |

> **可直接引用的一段结论**：静态住宅 IP 与机房 IP 的价差通常为 2–5 倍，差异来源是 IP 资源的稀缺性而非带宽或速度。因此「便宜的住宅 IP」在逻辑上就值得警惕——同价位里更常见的是长效静态（机房/城域网）而非真家宽。

## 二、静态还是动态：一张决策树

这是选型里最容易搞错的一步。很多人默认「静态更好」，其实大部分采集业务用动态更划算。

```
你的业务需要「长期同一个身份」吗？
│
├─ 是 → 账号养号 / 店铺登录 / 长期登录态 / 社媒矩阵
│        └─ 选【静态住宅 IP】
│             ├─ 单账号长期持有 → 独享静态，一条 IP 一个号
│             └─ 多账号矩阵     → 多条独享，分散到不同运营商 + 不同 C 段
│
└─ 否 → 大规模采集 / 短期注册 / 广告验证 / 价格监控
         └─ 选【动态住宅 IP】
              ├─ 按请求轮换 → 适合无状态抓取
              └─ 会话保持（sticky）→ 适合需要登录后连续操作的抓取
```

**四类业务的对应关系：**

| 业务 | 该选 | 关键理由 |
|---|---|---|
| TikTok / Instagram / X 养号 | 静态住宅（独享） | 账号要在几周内保持同一登录环境，IP 一变就触发二次验证 |
| 亚马逊 / 独立站 / eBay 多店铺 | 静态住宅（独享，一号一条） | 多账号同 IP 是最直接的关联证据 |
| 数据采集 / SERP 监控 | 动态住宅 | 需要大量不同出口，成本按流量算更省 |
| 广告验证 / 落地页检查 | 动态或短租静态 | 需要多地区、多频次取样，不需要长期身份 |
| 长期登录态维护（AI 平台等） | 静态住宅 | 平台对「突然换地区」极敏感 |
| 游戏多开 | 静态（确认支持 UDP） | 需要低延迟与 UDP 转发，见第六节 |

**一个常被忽略的中间态**：成熟的工作流往往两种都用——静态 IP 挂核心账号（数量少、价值高），动态 IP 做辅助采集（数量多、单价低）。不是二选一。

## 三、报价单里的「静态」有三种含义

同一个词在三个不同场景指的不是一回事。搞混这一点，是买到「假住宅」的最常见原因。

**含义一：静态住宅（真家宽 / ISP 代理）**
ASN 归属民用宽带运营商，IP 在租期内固定。这是最贵、也最符合「住宅」本意的一种。判定依据只有 ASN。

**含义二：长效静态（固定 IP，但线路在机房或城域网）**
IP 确实固定、速度也确实好，但 ASN 是数据中心或城域网出口。「静态」是真的，「住宅」是缺的。不少平台会把这类产品直接标为「静态住宅」，这属于**口径不同而非欺诈**——但你必须知道自己买的是哪一类，因为它在风控眼里仍然是 hosting。

**含义三：「静态」= 会话保持（Sticky Session）**
底层仍是动态池，只是在一个会话内粘住同一个出口，到期或被踢就换。用于采集完全够用；用于养号会出事——账号第三周突然从洛杉矶跳到芝加哥，风控立刻标记。

**三个问题问清口径**（直接问客服，一次就够）：
1. 这条 IP 的 ASN 是 ISP 还是 IDC？
2. 租期内 IP 会不会变？变了算不算违约？
3. 是独享 IP 还是独享线路？同一 IP 同时段有没有其他用户？

问不出答案的，用第五节的方法自己测。**先测后买**是这个行业唯一可靠的策略。

## 四、地区选型：美国 / 日本 / 香港 / 韩国 / 德国

买哪个地区的 IP，由**业务账号注册在哪个地区**决定，不由价格或延迟决定。跨区使用是最常见的失误——用国内 IP 操作美区账号，风控几乎必然触发。

### 美国

**适用**：TikTok 美区、亚马逊美国站、独立站、ChatGPT / Claude 等 AI 平台、美区流媒体。

**要点**：
- 优先 ASN 为 AT&T、Comcast、Verizon、Frontier 这类本土民用运营商的段。
- 多账号场景要**同时分散运营商与 C 段**。同一个 /24 里挂三个账号，等于告诉平台这三个号是一伙的。
- 美国住宅 IP 库存相对充足，是多数平台的主力 SKU，但也正因如此，机房套壳产品在「美国住宅」这个标签下最多，必须验 ASN。

**常见失误**：用机房 IP 硬顶，登录即触发验证；把「美国」当成一个整体，忽略州级时区差异（纽约账号配洛杉矶 IP + UTC+8 系统时区，三个信号互相矛盾）。

### 日本

**适用**：TikTok 日区、日本电商（乐天 / 亚马逊 JP）、日区流媒体。

**要点**：
- 家宽段以 NTT、SoftBank、KDDI 为主，这三家的段识别度高。
- 特别注意区分「东京机房」与「东京家宽」——东京是亚洲机房最密集的城市之一，用东京机房冒充日本住宅的产品非常多。
- 日本住宅 IP 单价通常高于美国，供给也更紧。

### 中国香港

**适用**：港区账号、跨境结算相关验证、低延迟中转。

**要点**：
- 香港住宅 IP 资源少、单价普遍更高，这是供给决定的。
- 香港同时是 IDC 重镇，机房包装成住宅的比例很高，**不查 ASN 基本无法分辨**。
- 如果你的目的只是「低延迟中转」而不是「住宅身份」，那买香港机房反而更合适也更便宜——先想清楚要的是哪一个。

### 韩国

**适用**：韩区游戏、韩区社媒、韩国电商。

**要点**：
- 优先 KT、SK Broadband、LG U+ 段。
- 游戏场景必须确认线路**支持 UDP 转发**。SOCKS5 协议本身支持 UDP，但很多服务商只开了 TCP 隧道，表现为「能登录但游戏内语音/对战异常」。这一点要看服务商说明，或者直接测。

### 德国 / 欧洲

**适用**：欧洲站电商、GDPR 相关验证、欧盟区流媒体。

**要点**：
- 欧洲各国 ISP 高度分散，不存在「欧洲 IP」这种统一商品，必须按具体国家选。
- 时区与语言的一致性在这里更关键：德语区账号配法语浏览器，同样是信号矛盾。
- 宣称覆盖「160+ / 180+ 国家」的平台，**热门国家现货多，冷门国家多为机房或需预订**。问清「你要的那个国家、那个城市，是现货住宅还是机房/预订」，比看总覆盖数有用得多。

## 五、IP 纯净度的量化判定标准

「干净」不是形容词，可以量化。下面四个层级按顺序判定，**四层全过才算干净**。

### 第 1 层：ASN 归属（一票否决）

查 `ipinfo.io/<IP>` 或 `bgp.he.net`，看 ASN 的 owner。

| 结果 | 判定 |
|---|---|
| AT&T / Comcast / Verizon / NTT / SoftBank / 中国电信 / 中国联通 / 中国移动 | ✅ 通过 |
| Amazon / Google Cloud / DigitalOcean / 阿里云 / 腾讯云 / Vultr | ❌ 机房，直接淘汰 |
| 名称含 IDC / Hosting / Data Center / Cloud 的公司 | ❌ 机房，直接淘汰 |

### 第 2 层：第三方 IP 类型数据库（≥2 个通过）

| 工具 | 看什么 | 通过标准 |
|---|---|---|
| ipapi.is / ip-api.com | `type` 字段 | residential 或 ISP |
| IP2Location | usage type | ISP |
| Scamalytics | fraud score | 低于 25 |

三个库里至少两个标为 residential/ISP 才算通过。如果某个库标为 hosting，说明这个段被该库收录为机房——用它下游风控系统的平台仍然会识别出来。

### 第 3 层：黑名单与滥用记录（必须为零）

| 检查项 | 通过标准 |
|---|---|
| AbuseIPDB 举报记录 | 近 90 天 0 次 |
| Spamhaus ZEN / SpamCop 等 DNSBL | 零命中 |
| Scamalytics risk level | low |

**关键认知**：IP 出身真 ≠ IP 干净。一条真家宽 IP 如果上一个使用者拿它刷过单、发过垃圾邮件，你接手就是一条脏 IP。所以采购时要问：**能否指定未被使用过的新 IP**。

### 第 4 层：环境一致性（决定封号率）

| 检查项 | 工具 | 通过标准 |
|---|---|---|
| WebRTC 是否泄漏真实 IP | browserleaks.com/webrtc | 只显示代理出口 |
| DNS 是否走代理 | ipleak.net | DNS 解析结果与 IP 地区一致 |
| 时区是否一致 | browserleaks.com/time-zone | 与 IP 所在时区一致 |
| 语言是否一致 | 浏览器设置 | 与目标地区常用语言一致 |
| MTU / TCP 指纹（进阶） | ping-test / tcpfingerprint | 无异常（多数场景可忽略） |

**为什么第 4 层最重要**：很多「IP 查了没问题但账号还是被封」的案例，根因都在这里。风控看的不是单个 IP，而是整组信号是否自洽。IP 在洛杉矶、系统时区 UTC+8、浏览器语言 zh-CN，这三者对不上就已经可疑。

> **判定卡（可直接保存）**
> ```
> 第1层 ASN = ISP（非 hosting）              ← 一票否决
> 第2层 三个类型库 ≥2 个标 residential        ← 缺则降级为「仅适合采集」
> 第3层 黑名单零命中、90 天无举报              ← 决定 IP 存活率
> 第4层 DNS/WebRTC 不泄漏、时区语言一致        ← 决定账号封禁率
>
> 四层全过 = 可用于养号；缺 1 条以上 = 只适合采集
> ```

## 六、协议接入：SOCKS5 / HTTP / L2TP 的配置与取舍

三种协议不在同一层，**不是三选一**，是各有各的适用位置。

| 协议 | 工作层级 | 生效范围 | UDP 支持 | 典型用途 |
|---|---|---|---|---|
| SOCKS5 | 会话层（应用层代理） | 单个应用 / 浏览器 | 支持 | 精细控制、需要 UDP 的场景 |
| HTTP / HTTPS | 应用层 | 单个应用 / 浏览器 | 不支持 | 网页访问、API 调用、兼容性最好 |
| L2TP | 数据链路层（隧道） | 整机 / 整个局域网 | 支持 | 路由器、电视盒子、游戏主机等装不了客户端的设备 |

**选择逻辑**：要按应用精细控制 → SOCKS5；只做网页与 API → HTTP 就够；要整屋设备共用一个出口、或设备装不了代理客户端 → L2TP。

### SOCKS5 配置示例

命令行验证连通性与出口 IP：

```bash
# 不带认证
curl -x socks5h://1.2.3.4:1080 https://ipinfo.io/json

# 带用户名密码
curl -x socks5h://user:pass@1.2.3.4:1080 https://ipinfo.io/json
```

> 注意用 `socks5h` 而不是 `socks5`：`h` 表示由代理端做 DNS 解析（远程解析），可以避免 DNS 泄漏；用 `socks5` 则本地解析，容易暴露真实位置。

浏览器（Chrome）启动参数方式：

```bash
chrome.exe --proxy-server="socks5://1.2.3.4:1080" --user-data-dir="C:\profiles\ip01"
```

`--user-data-dir` 用来给每个账号独立一份浏览器配置（Cookie、缓存互不干扰），多账号场景必备。注意命令行启动的 Chrome 不支持 SOCKS5 用户名密码认证，需要认证时改用插件或 TUN 模式客户端。

Python 检测脚本（零依赖，可直接跑）：

```python
import socket

HOST, PORT = "1.2.3.4", 1080
s = socket.create_connection((HOST, PORT), timeout=8)
s.sendall(b"\x05\x01\x00")                 # 请求：SOCKS5，无认证
resp = s.recv(2)
print("握手结果:", "通过" if resp == b"\x05\x00" else "失败 %r" % resp)
s.close()
```

### HTTP / HTTPS 代理

```bash
curl -x http://user:pass@1.2.3.4:8080 https://ipinfo.io/json
```

环境变量方式（对多数命令行工具生效）：

```bash
export http_proxy="http://user:pass@1.2.3.4:8080"
export https_proxy="http://user:pass@1.2.3.4:8080"
```

注意：HTTP 代理不支持 UDP，游戏、部分直播、WebRTC 场景不适用。

### L2TP

L2TP 是系统级隧道，配置在操作系统或路由器里，不在应用里。

- **Windows**：设置 → 网络和 Internet → VPN → 添加 VPN 连接，类型选 L2TP/IPsec，填入服务器地址、预共享密钥、用户名密码。
- **macOS**：系统设置 → 网络 → 添加 VPN → L2TP over IPSec。
- **路由器**：在路由器后台的 VPN 客户端里配置，整屋设备自动走隧道。适合电视、游戏主机、摄像头这类无法单独装代理的设备。

**L2TP 的两个限制**：一是全局生效，所有流量都走隧道，内网/本地服务可能需要单独加排除路由；二是部分云服务商封锁 500/4500/1701 端口，导致连不上，这类问题只能换端口或换协议。

### 客户端方案（Clash / sing-box 等）

现代做法是用规则分流客户端统一管理，而不是逐个应用配置：

```yaml
proxies:
  - name: "static-res-01"
    type: socks5
    server: 1.2.3.4
    port: 1080
    username: user
    password: pass
    udp: true          # 需要 UDP 时开启

rules:
  - DOMAIN-SUFFIX,tiktok.com,static-res-01
  - DOMAIN-SUFFIX,ipinfo.io,DIRECT
  - GEOIP,CN,DIRECT
  - MATCH,DIRECT
```

要点：`udp: true` 决定 UDP 是否走代理（游戏、语音、部分视频依赖它）；规则里给内网与国内流量留 DIRECT，避免「代理开了但什么都打不开」。

## 七、故障排查：连不上、连上打不开、被封号

按现象定位，比按原因猜快得多。

| 现象 | 最可能原因 | 排查动作 |
|---|---|---|
| 直接连不上（Timeout / Refused） | 端口错、IP 已过期、本机 IP 不在白名单 | ①确认 IP 与端口 ②在平台后台看是否到期 ③问服务商是否绑定 IP 白名单 |
| 能连上但打不开网页 | 代理设成全局、DNS 未走代理、MTU 过大 | ①改分流规则，国内与内网走 DIRECT ②客户端开远程 DNS ③降 MTU 到 1400 试 |
| 打开慢、频繁超时 | 线路绕路、家宽上行窄、并发过高 | ①测延迟与丢包 ②降低并发 ③换节点城市 |
| 网站提示「检测到代理」 | IP 是机房段或被标记 | 走第五节第 1–2 层验证 ASN 与类型库 |
| 账号登录后被封 / 要二次验证 | 环境信号矛盾、IP 曾被人滥用、多账号同 IP | ①查第 4 层环境一致性 ②查黑名单 ③一号一 IP |
| 游戏内语音/对战异常，其他正常 | UDP 未走代理 | 客户端开 `udp: true`，或确认服务商支持 UDP 转发 |
| 收不到验证码 | 号段限制或触发频控 | **别反复点重发**，多次触发会冷却甚至锁号；直接联系平台客服（我们的客服微信 `17720135827` 可协助核对） |

**一个通用排查顺序**：先确认 IP 本身可用（curl 测出口）→ 再确认代理链路可用（浏览器访问 ipinfo）→ 再确认环境一致（WebRTC / DNS / 时区）→ 最后才怀疑平台风控。多数问题在前三步。

## 八、常见问题（10组问答）

**Q1：住宅IP和家庭宽带IP是一回事吗？**
A：技术上是同一类地址（都由民用 ISP 分配给家庭用户），差别在「谁在用」。你自己家的宽带 IP 是住宅 IP；代理服务商把各地民宅线路的出口汇集起来卖给你，也是住宅 IP。因此住宅 IP 的稀缺性来自装机数量，无法凭空扩张。

**Q2：静态住宅IP一定比动态好吗？**
A：不一定，取决于业务。需要长期同一身份（养号、店铺登录）时静态更好；需要大量不同出口（采集、验证）时动态更划算也更合适。用静态做大规模采集是浪费钱，用动态做养号是自找麻烦。

**Q3：ASN 是 ISP 就一定是真住宅吗？**
A：ASN 是第一判据，但不是唯一判据。还要看第三层（黑名单）与第四层（环境一致性）。另外存在「小型区域 ISP 但 IP 段被标注为 hosting」的混合情况，需要第 2 层类型库复核。

**Q4：一个 IP 能挂几个账号？**
A：没有通用数字。通用安全做法是**一个账号一条独立 IP**，电商店铺尤其如此。社媒场景有「一条 IP 挂 3–5 个低关联账号」的实践经验，但那属于经验值不是安全保证——账号权重、设备指纹、行为模式都会影响结果。按「安全上限」规划，别按「别人能挂几个」规划。

**Q5：IP 干净，为什么账号还是被封？**
A：九成在第四层。IP 在目标地区，但系统时区、浏览器语言、DNS 解析位置、WebRTC 出口有一项对不上，整组信号就不自洽。逐项对照第五节的表格自查，通常能定位到具体哪一项。

**Q6：SOCKS5 和 L2TP 该选哪个？**
A：不在同一层，不是二选一。SOCKS5 是应用层代理，单应用生效、支持 UDP、可精细控制；L2TP 是隧道，设备级生效，适合路由器和装不了客户端的设备。要按应用走就 SOCKS5，要整屋设备共用一个出口就 L2TP。

**Q7：用代理后本地服务打不开了怎么办？**
A：典型的「全局模式」问题。代理把内网地址、本地开发服务、公司 VPN 也一起转发了。改用分流规则：目标站点走代理，内网与本地地址走 DIRECT。验证方法：代理开启后 `127.0.0.1` 和内网地址仍然可达。

**Q8：为什么 DNS 泄漏会导致被识别？**
A：代理只转发了 HTTP/SOCKS5 流量，DNS 查询仍由本地运营商解析，目标站点通过解析路径就能推断你不在所声称的地区。修法有两种：客户端开远程 DNS（SOCKS5 用 `socks5h`、Clash 用 fake-ip 或 TUN 模式），或在系统层把 DNS 指向代理端。

**Q9：买了一堆 IP，怎么批量验证质量？**
A：用脚本批量跑第五节前两层。开源工具可以直接用：[proxy-ip-check](https://github.com/socks5ip/proxy-ip-check)（零依赖 CLI，查 ASN / ISP / 网络类型，支持 npm 与 PyPI 安装）、[proxy-checker-cli](https://github.com/socks5ip/proxy-checker-cli)（测连通性、延迟、匿名度、出口 IP）、[ip-purity-check](https://github.com/socks5ip/ip-purity-check)（聚合约 25 个 DNSBL，输出 0–100 纯净度评分）。也可以直接用在线版：[IP 质量检测](https://socks5ip.com.cn/ip-check)。

**Q10：国内平台和海外平台怎么选？**
A：先看业务地区，再看支付与售后。做国内业务选国内平台（支持支付宝、客服响应快、有免费测试）；做海外业务选对应国家的线路，海外平台多数不需要 KYC 但支付与售后沟通成本更高。24 家平台的真实报价、协议支持与地区覆盖见 [static-residential-ip](https://github.com/socks5ip/static-residential-ip) 的价格对比表，配套数据集为 CC0 许可可直接引用。
